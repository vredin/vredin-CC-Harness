# /design-system — From Goal to Full Solution Research

Use this when you have a goal but no formal specification yet. Generates a draft TZ from your goal via clarifying questions, then runs the full `/analyze-spec` pipeline on it.

Output: same `final-report.md` + optional PDF, with Section 1 marked as a generated draft (not a quoted TZ).

## When to use

- **Greenfield project.** You know what you want to achieve, but haven't designed the system.
- **Build-vs-buy decision.** You want to know if ready-made solutions exist before specifying custom development.
- **Sanity-check an idea** before investing time into writing a formal TZ.

## When NOT to use

- You already have a TZ document → use `/analyze-spec` directly.
- You want pure brainstorming without analysis → use the built-in `brainstorming` skill standalone.
- You want pure tool-comparison research without architecture → use `/analyze-spec` on a one-line TZ describing the category you want compared.

---

## STEP 0 — Capture the goal

Read `$ARGUMENTS`. If empty, ask the user one question:

> Какую систему хочешь спроектировать? Опиши цель в 1-3 предложениях.

Wait for the response. Save the raw goal-statement to memory for Step 1.

---

## STEP 1 — Clarifying questions (3-5 questions max)

Ask the user **at most 5 questions**, one combined message, covering ONLY these dimensions:

1. **Target user / operator** — кто будет пользоваться системой? Один человек, команда, конечный клиент?
2. **Scale** — сколько раз в день/неделю система запускается? Сколько объектов обрабатывается?
3. **Hard constraints** — есть ли явные ограничения по бюджету, команде, инфраструктуре, юрисдикции?
4. **Success criteria** — что значит «работает»? Какой результат пользователь хочет видеть?
5. **Time horizon** — MVP за недели или полноценная система за месяцы?

**Do NOT ask about:**
- Technical implementation (фреймворки, API, БД) — это работа research-стадии
- Detailed acceptance metrics — `report-writer` предложит метрики сам
- Anything that can be inferred from goal + scale + constraints

**Do NOT ask >5 questions.** Если что-то осталось неясным — это попадает в `open_questions` сгенерированного TZ.

---

## STEP 2 — Generate draft TZ

Synthesize goal + answers into a draft saved to `specs/draft-<slug>.md`:

```markdown
<!-- Generated by /design-system from goal-statement on <Kyiv-time> -->
<!-- This is a DRAFT TZ produced from a goal-statement, not a stakeholder document. -->
<!-- Section 1 of the final report will explicitly mark this as auto-generated. -->

# Цель проекта (verbatim from user)

<goal-statement, exact wording>

# Контекст использования

- Целевой пользователь: <answer to Q1>
- Масштаб: <answer to Q2>
- Жёсткие ограничения: <answer to Q3>
- Критерий успеха: <answer to Q4>
- Горизонт: <answer to Q5>

# Что система должна делать [INFERRED FROM GOAL]

<3-7 functional bullets that follow logically from goal + context.
Mark each with [INFERRED] tag.>

- [INFERRED] <functional requirement 1>
- [INFERRED] <functional requirement 2>
...

# Что НЕ определено пользователем

<list of dimensions the user did NOT specify — these become open_questions
in spec.yaml and section 5 of the final report>

- <undefined dimension 1>
- <undefined dimension 2>
...
```

**Slug derivation:** kebab-case from first 4-6 words of goal. E.g., "система перевода видео с английского" → `video-translation-system`.

Save to `specs/draft-<slug>.md`. Announce to user: `Draft TZ ready at <path>. Starting analyze-spec pipeline...`

---

## STEP 3 — Run analyze-spec on draft

Invoke `/analyze-spec specs/draft-<slug>.md` with two extra context variables:

```
SOURCE_TAG=design_from_goal
DRAFT_TZ=true
```

The full pipeline (8 stages) runs unchanged. Three things are different in the report due to `SOURCE_TAG=design_from_goal`:

1. **Section 1** — `report-writer` adds a top note: *«Эта спецификация создана автоматически из цели пользователя. Все [INFERRED]-пункты — допущения системы, не утверждения заказчика.»*

2. **Section 4** — researcher's emphasis shifts from "критика выбранной технологии" to "поиск готовых решений + построение custom-стека". The build-vs-buy comparison appears prominently in subsection 4.1 BEFORE technology-specific subsections.

3. **Section 7** — instead of "Возможные изменения исходного ТЗ", title becomes "Варианты охвата системы". Subsections 7.1 / 7.2 / 7.3 represent **scope levels** for a working solution:
   - 7.1 минимум — самое простое работающее решение, чаще всего готовый SaaS
   - 7.2 среднее — гибрид готовых компонентов + минимальная склейка
   - 7.3 максимум — полностью custom стек

---

## STEP 4 — Hand off to user

When `/analyze-spec` completes, the deliverable is at `specs/analysis/<slug>/final-report.md` (+ `.pdf` if `PDF_AT_END=yes`). The same Step 8 announcement applies, with one addition: explicit reminder that this report is based on a generated draft.

---

## Failure modes

- **User refuses to answer clarifying questions** → proceed with goal + sane defaults; mark every default as `[default — confirm]` in `open_questions` of the draft TZ.
- **Goal is too vague** ("хочу систему лучшую в мире") → ask one focused follow-up: "Что конкретно эта система должна делать пользователю?"
- **Brainstorming reveals user actually has a TZ already** → save what they have to `specs/<slug>.md` and run `/analyze-spec` directly, skip the draft generation.

---

## What this command does NOT do

- Does not write code, prototypes, or implementation guides
- Does not perform user research / interviews — operates on what user states
- Does not commit to a recommendation — same decision-support stance as `/analyze-spec`

## Why a wrapper is enough (not a separate framework)

The existing pipeline already does:
- Categorical breadth research (researcher Step 3 cheatsheet)
- Build-vs-buy via Section 4 alternatives tables
- Operational dimensions audit (Diablo + idea-atomizer)
- Architecture deep-dive (researcher Step 3b)
- Hardware compatibility check (researcher Step 3b 2a)
- Token / cost analysis for LLM-driven products (researcher Step 3b 2b)
- Section 7 trade-off space exploration

The only thing missing for greenfield use was the input shape — a thin goal-statement instead of a multi-paragraph TZ. This wrapper bridges that gap and reuses 100% of the existing analytical machinery.
